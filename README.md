# Lava_test 固态硬盘全段测试看板

面向 SSD 产线的机台测试数据看板：把**工站、机柜、服务器、盘位**与测试日志关联起来，
帮现场看在制状态、产能瓶颈、不良与报错。

> **当前进度：阶段 1（核心看板）已完成**，可双击打开验收。
> 后续阶段见 [路线图](#路线图)。

---

## 快速开始

**看界面** —— 双击 `Lava_test看板.html`，然后点顶栏的 **「生成模拟数据」**。

会按真实车间配置生成一整套数据（**13,585 个盘位**），十个视图立刻有内容。

**接真实设备** —— 点顶栏 **「设备台账」** → 选 `设备IP情况.xlsx` → 应用导入。
看板随即切换到**真实台账模式**：设备编号变成 `S35#-3` 这样的真实机柜号+位号，
并带上各设备的 IP，供桥接服务连接。

**连现场数据** —— 双击 `bridge\启动桥接服务.bat`，然后**改用
`http://127.0.0.1:8770/` 打开看板**（不是双击 HTML 文件）。

> 为什么要换地址打开：Chrome/Edge 在 `file://` 下会禁用 IndexedDB，
> 看板只能退回容量受限的降级存储（页面顶部会有橙色横幅）。
> `127.0.0.1` 是安全上下文，存储全功能可用。

```bash
# 改代码后重新构建
node build.js

# 构建 + 校验 + 测试一条龙
npm run verify
```

> ⚠️ **直接改 `Lava_test看板.html` 是没用的** —— 它是构建产物。
> 要改的是 `src/`，改完跑 `node build.js`。

## 车间配置（来自设备台账实测）

设备数取自 `设备IP情况.xlsx`（448 台可接入设备 / 48 机柜 / 494 个 IP），
由 `src/ingest/ledger.js` 解析。

| 工序 | 全称 | 设备 | 单台容量 | 单轮时长 | 同时在线 | 日产能 | 相对整线 |
|---|---|---|---|---|---|---|---|
| **ICT** | In-Circuit Test | 1 台 | 1 盘位 | **28.8 秒** | 1 | **3,000 ← 节拍源** | 1.00× |
| **FUNCTION** | Function Test | 16 台 | 16 盘位 | 30 分 | 256 | 12,288 | 4.10× |
| **BIST** | Built-In Self-Test | 19 台 | 256 盘位 | 28 小时 | 4,864 | 4,169 | 1.39× |
| **ESS** | Environmental Stress Screening | 18 台 | 128 盘位 | 13 小时 | 2,304 | 4,254 | 1.42× |
| **FINAL** | Final Test | 311 台 | 16 盘位 | 31 小时 | 4,976 | 3,852 | 1.28× |
| **ORT** | Ongoing Reliability Test | 33 台 | 16 盘位 | 7 天 | 528 | 75 | 旁路 2.5% |
| **CUS** | Customization | 41 台 | 16 盘位 | 3 小时 | 656 | 5,248 | 1.75× |

**盘位总数 13,585**。物理结构：除 ICT / BIST / ESS 是独立设备外，其余为 **机柜 → 9 台服务器 → 每台 16 盘位**。

**工序顺序**：`ICT → FUNCTION → BIST → ESS → FINAL → CUS`，ORT 为**旁路抽检**（2.5%）。

### ★ 整线产能跟 ICT 走

现场明确：**所有工序产能以 ICT 为准**。所以 `capacity.js` 不是「取各工序理论产能的最小值」，
而是**以 ICT 的实测日产能 3,000 块/天为整线节拍**，其余工序只判断**跟不跟得上**。

这一条很关键，因为 **ICT 的理论产能是错的**：

```
标称 6 秒/块  → 理论 14,400 块/天   ← 这 6 秒是纯测试时间，不含上下料
实测 3,000 块/天 → 有效 28.8 秒/块  （6 秒测试 + 22.8 秒上下料）
```

差了 **4.8 倍**。若按理论值取最小值，ICT 会被算成产能大户，真瓶颈反而被掩盖。

### 一条强验证：ORT 的 33 台

```
整线节拍 3,000 块/天 × 2.5% = 75 块/天   ← 抽检需求
ORT 33 台 × 16 盘位 ÷ 7 天 = 75.4 块/天  ← 实际能力
```

**匹配度 99.4%**。这个吻合度说明两件事：
1. 台账声明的 33 台是真实配置（明细里另有 28 台借用机、其中 8 台在「故障机台」，不计入）
2. ORT 必须是**旁路**而非串行 —— 若串行，它 75 块/天的吞吐会成为整线瓶颈（比 FINAL 还低 50 倍）

### 各工序余量

除 ICT（节拍源）与 ORT（旁路）外，**全部工序都在 3,000 块/天以上**，与现场「产能完全够」一致。
最紧的是 FINAL（1.28×），其次是 BIST（1.39×）。

## 设备台账导入

顶栏「设备台账」→ 选 `设备IP情况.xlsx` → 预览差异 → 应用。

### 拓扑有两条来源

| 模式 | 设备编号 | 何时使用 |
|---|---|---|
| **合成** | `SRV-N-001` / `CAB-N-01` | 未导入台账时，按工站配置的「N 台设备」生成占位结构 |
| **台账** | `S35#-3` / `BIST-61#` | 导入台账后，用真实机柜号 + 位号 |

导入台账会切到台账模式 —— **现场标号与看板一致**，桥接阶段才能把巡检到的 IP 对应到具体设备。

台账未覆盖的工站（如 ICT 单机台不在这份服务器台账里）按配置补齐，不会丢失。

### 解析器要处理的现实问题

这份台账是人工维护的，结构不规整，解析器逐条应对：

| 情况 | 处理 |
|---|---|
| 一张工作表里有**两张子表**（服务器表 + BIST/ESS 箱体表），列含义不同 | 按表头切块，各自解析列 |
| 箱体表的「分类」列装的是**箱号**（61#），品类却在「类别」列 | 识别箱号形态，分列取用 |
| 机柜号**只在每组首行**出现 | 向下继承 |
| 分类也落在首列（`量产_function`） | 按前缀识别，不当机柜 |
| 「WTS借用设备」标记在 D 列与 F 列之间**漂移** | 扫全部工位列 |
| 型号串混进工位列（`鸾起:phoenix-E-S256-BI`） | 按「含冒号或过长」过滤 |
| 「服务器位置」列有时写的是工站名而非数字 | 非数字位号回退为**按柜独立序号** |
| A 列混进「故障机台」「新增新华3服务器」等标签 | 按形态筛掉并记入警告 |

### 零依赖

`src/ingest/parsers/xlsx.js` 自己实现 zip 中央目录解析 + xlsx XML 解析，
解压用 `DecompressionStream`（浏览器与 Node 18+ 通用）。
**同一份代码在页面和 Node 脚本里都能跑**，不必为测试另写一套。

### IP 映射

「设备清单」页签列出全部设备及其 IP，带校验：

- **缺 IP** / **格式错** / **IP 重复**（重复会让桥接把数据归到错误的设备上）
- 可逐条改 IP，改了重复值会提示确认
- 导出 **CSV**（完整字段）或 **桥接连接清单 JSON**（`{ip, station, equipmentId, cabinet}`，
  桥接服务直接读）

## 架构要点

### 源码模块化 → 构建成单文件

源码拆成 41 个模块便于维护和测试，`build.js` 合并成一个 HTML 交付 —— 现场仍是**双击即用**。

**为什么用普通脚本拼接而不是 ES Module**：ES Module 在 `file://` 下会被 CORS 拦截，双击打不开。

> ⚠️ 构建脚本用**函数**而非字符串作为 `String.replace` 的替换值。
> 传字符串时 `$&` `` $` `` `$'` `$n` 会被解释为特殊序列，
> 源码里出现 `'...$'` 这类字面量就会被静默破坏。`build.js --check` 会校验**注入后**的产物，能拦住这类问题。

### 存储分层

12,737 个盘位的全量 JSON 超过 `localStorage` 5 MB 上限，因此：

| 层 | 存什么 | 介质 |
|---|---|---|
| 配置层 | 规则表、设置、UI 偏好 | `localStorage`（几十 KB） |
| 数据层 | 盘位、记录、不良、报错、工单 | **IndexedDB**（降级时用紧凑 localStorage，再不行用内存） |
| 会话层 | 当前视图、筛选、折叠 | 内存 |

**降级是必需的**：Chrome/Edge 在 `file://` 下会禁用 IndexedDB。页面会自动探测并降级，
同时在顶部显示横幅告知。

> **推荐由桥接服务托管页面**（`http://127.0.0.1:8770/`，安全上下文）以获得完整容量。
> 该服务在阶段 3 交付；在此之前双击打开也能用，只是容量受限。

### 渲染：逐格显示测试状态 + 隐藏空载设备

平面图按工站分区，每台设备一张卡，卡内是**逐格彩色网格** —— 一盘位一格，
颜色即状态（在测 / 通过 / 失败 / 异常终止 / 维护 / 损坏）。

**空载设备默认隐藏。** 产线不会一直满测；满配 12,737 格若大部分是空位，
全画出来反而看不出哪台在跑。图例处可勾选「显示空载设备」看全貌。

实测：模拟数据下 490/503 台在跑，页面渲染 12,576 格。

刷新走 **增量补丁**：维护 `slotKey → HTMLElement` 索引，只改变化的格，
不重建子树。索引不靠给每个格子挂 `data` 属性（会多出 ~350KB），
而是利用「`querySelectorAll` 返回文档序 == 发射顺序」，按设备循环 O(n) 对齐。

> 这条路径有专门的测试覆盖：冒烟测试的 DOM 桩会把渲染出的 HTML 解析成
> 「按工站分组的格集合」，使 `buildIndex` 真的建起索引，
> 再改一个盘位状态、调 `refresh`，断言**只 patch 了 1 格**且 class 正确更新。
> 桩若在这里返回空，补丁路径就是「看起来测了其实没测」——
> 这正是索引对齐最容易出错的地方。

其他：
- **折叠**：按工站折叠，收起时该区不参与布局
- **CSS**：`content-visibility: auto` 让浏览器跳过视口外的布局与绘制
- **热力图**（智慧看板）：12,737 格 canvas 默认不绘制，点按钮才画

### 图表零依赖

RDIMM 从 CDN 加载 ECharts，现场断网即失效。本项目手写 SVG 柱状/折线/环形图，
约 200 行覆盖全部需求，打包后仍 < 20 KB、**完全离线可用**、可导出 PNG。

### 主题：深色 / 护眼 / 跟随系统

顶栏按钮循环切换。护眼模式是**暖色浅底**（米黄偏豆沙绿），长时间盯屏降低眼疲劳。

```css
html[data-theme="dark"] { /* 默认，工业现场弱光环境 */ }
html[data-theme="eye"]  { /* 暖色浅底，对比度压低一档 */ }
```

实现上有两条硬约束：

**① 所有颜色必须走 CSS 变量。** 组件里不允许出现硬编码色值 ——
否则新增主题时必然漏改，出现「大部分变了、某块还是原来的底色」。
构建后的产物里如果引用了未定义的变量，测试会直接报错。
当前 **51 个变量全部有定义**，护眼主题覆盖了其中 **55 个颜色变量**。

**② 护眼主题下状态色整体加深。** 深色主题的亮绿（`#39d353`）放到浅底上几乎看不见，
因此两套主题各自定义了盘位状态色与工站色。

主题在 `App.boot()` 的最开头应用，避免「先按深色画一帧再跳成浅色」的闪屏。
`跟随系统` 模式会监听 `prefers-color-scheme` 实时切换。

## 关键设计决策

### 「异常终止」绝不是「失败」

```
fail  (红) = 产品不合格        → 计入良率分母
abort (紫) = 数据不完整        → 不计入分母
             （断电 / 超时 / 中间取料）
```

两者混在一起会让良率严重失真。这一条贯穿：盘位状态、良率计算、报表口径。

### 判定引擎留审计

每次判定都写**不可变流水**（原文、命中规则、确认人、时间），可完整回溯。
规则变更**只影响后续判定，不重算历史** —— 这是有意设计。

三种结论：
- `functional` 功能性不良 → 写入不良记录并**自动确认**
- `nonfunctional` 非功能性 → 只留流水（如机柜侧事件）
- `unknown` 待确认 → 写入不良但**等人工确认**，平面图对应盘位显示黄框

### 同箱 / 同柜连带追溯 ★

单箱 256 盘、单柜 144 盘 —— 一次设备异常的影响面是数十到数百块盘。
这是单件流产线没有的场景，也是「箱体异常须整箱判废重测」规则的依据。

### 待确认项参数化，不写死

规范里 6 项 🔴 未确认事项全部做成配置：工站设备数、工序顺序、良率口径、ORT 停线判据……
其中 **ORT 停线判据未定，因此系统只提示不自动停线**（避免误停）。


**当前：266 项断言全部通过。**

### 端到端演练（`tools/e2e-sim.js`）★

**不连任何产线设备**，在本机把整条链路跑通：

```
导入真实台账 → 造仿真日志 → 桥接扫描 → 增量拉取 → 解析入库
  → 盘位状态更新 → 不良生成 → 幂等 → 追溯 → 视图渲染
```

**这个演练不是锦上添花 —— 第一次跑就发现了一个致命缺口**：
`pipeline.js` 把解析结果写进 `records` 表，但**从不写 `slots` 表**，
意味着拉再多日志平面图也不会变。每一段单独测都过，
但「拉完日志看板该变」这件事只有端到端才验证得到。

演练还顺带验证了两个设计真的成立：
- **增量 + 幂等**：增量模式第二轮不下载；强制全量重拉记录不翻倍
- **解析器注册表扩展点**：注册一个解析器文件，SSD 程序风格的日志从解析出 0 条变成 20 条，
  **调用方一行没改**

### 三类结构性校验（比功能测试更能拦住回归）

1. **构建产物完整性** —— 逐字符比对注入后的脚本与源码，拦住 `replace` 替换陷阱
2. **主题变量完备性** —— 每个 `var(--x)` 都要有定义，且护眼主题覆盖全部颜色变量
3. **存储结构一致性** —— 扫所有 `Repo.xxx('store')` 调用点核对已声明，并检查 `IDB_VERSION` 与自愈逻辑

## 已知限制

| 限制 | 说明 |
|---|---|
| **数据接入未接通** | 阶段 3 交付。目前只能靠模拟数据或导入 JSON |
